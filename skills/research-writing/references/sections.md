# 论文章节写作指南

| 章节 | 写作目标与所需依据 | 完成检查 |
|---|---|---|
| 标题 | 准确点明研究任务与核心机制、视角或发现 | 与实际验证范围一致；避免无实质指向的空泛夸大词 |
| 摘要 | 按“任务背景—核心缺口—方法机制—主要结果—结论意义”紧凑闭环 | 独立成文（不写引用编号与未定义生僻缩写）；数值与正文完全一致；未完成研究用计划式表述 |
| Introduction | 从任务价值引出固有困难、已有路线局限、本文洞察、方法概览与贡献 | 每项贡献均在方法或实验中有明确落点；背景铺垫直接服务于本文问题 |
| Related Work | 按技术路线或问题维度分类综述，阐明演进脉络、代表作局限与本文定位 | 分类标准清晰，覆盖关键文献，对比客观且指明适用条件，引用真实可查 |
| 方法 | 问题形式化定义后，先给整体框架概览，再分模块阐明机制、符号与设计动机 | 输入输出与任务定义一致，符号首次出现即定义，模块作用与挑战一一对应 |
| 理论分析 | 在明确定义与假设下陈述性质、复杂度或保证，并配合直观解释 | 假设条件、结论适用范围与实验观察严格区分；无理论依据时不强凑形式化证明 |
| 实验 | 用具体实验设置、主实验对比、消融与分析实验逐一检验核心贡献与模块作用 | 数据集、划分、基线、指标方向、超参及数值与原始记录及图表完全一致 |
| 讨论与局限 | 深入解释实验现象、方法适用边界、开销权衡或失败案例 | 事实观察与推测解释分开标记；局限性具体指向假设、场景或规模边界 |
| 结论 | 简要回应研究问题，总结已被证据支持的核心贡献，展望具体后续方向 | 不引入正文未证明的新结论或新数据；未来工作保持计划语气 |

## 标题与摘要

- **标题**：优先采用“核心机制/属性 + 研究任务”或“针对特定挑战的方案”结构。避免仅堆砌 `Novel`、`Effective`、`Advanced` 等主观修饰词，改用能体现技术特征的具体限定（如 ` Contrastive ...`、`Training-Free ...`、`... under Label Noise`）。
- **摘要五要素**：
  1. **任务与场景**（1句）：锁定具体研究对象及其应用或科学背景。
  2. **核心缺口**（1句）：点明已有方法在何种条件或机制上面临瓶颈（用 `However,` 等转折精准切入）。
  3. **本文方案**（1–2句）：概括整体路线与核心组件如何协同破解该瓶颈，避免罗列未解释的内部模块代号。
  4. **验证与结果**（1–2句）：交代评测基准范围与主要定量/定性观察，对比基准与指标需具体，不空喊“全面超越”。
  5. **意义或可用性**（可选，半句至1句）：点明结论启示或开源计划。

## Introduction 与贡献列表

- **漏斗式推进**：从具体任务及其价值切入 → 剖析问题困难与现有方法在机制上的局限（说明“为何做不好”，而非仅说“精度不够高”） → 提出本文核心直觉（Insight）与方法设计 → 简述实验验证方式与核心结果 → 归纳贡献列表。
- **贡献列表（Contributions）规范**：
  - 区分贡献类型：**问题/视角创新**、**方法/算法设计**、**理论/复杂度分析**、**实验发现/新基准/开源系统**。
  - 避免将常规实验流程写成空洞凑数项（如单独列一条“我们在三个数据集上进行了大量实验”）；若将实验验证作为最后一条，须点明具体的**验证范围与关键实验结论**（例如验证了何种泛化性、效率优势或模块规律）。
  - 贡献条数服从实际增量（通常 2–4 条），且每条都必须能在后文找到对应小节或图表支撑。

## Related Work

- **分类综述而非逐篇罗列**：按任务设定、建模机制、核心假设或技术流派组织小节。每段先概括一类工作的共同思路，再剖析代表性方法的适用边界，最后自然引出本文方案与它们的关联与区别，避免写成“A 做了 X；B 做了 Y；C 做了 Z”的文献摘要流水账。
- **有边界地客观对比**：批评前人工作时指明前置条件，例如“该类方法依赖成对标注数据；本文考察无成对标注场景”，而不无依据地贬低为“已有方法均无法使用”。
- **引用规范**：引用编号附着在具体作者、方法名或明确的学术论断上，格式遵循目标模板。未核实的文献显式标为 `[CITE: 待核实...]`，绝不生成虚构文献。

## 方法与理论表述

- **自顶向下展开**：
  1. **问题定义与符号（Problem Formulation）**：明确输入空间、输出目标、约束条件与核心数学符号。
  2. **整体框架概览（Overview）**：配合架构图说明数据流向，明确区分**训练阶段**与**推理阶段**的输入、模块调用与损失计算。
  3. **核心模块详述**：每个核心子节遵循**“该模块解决什么子问题 → 数学/算法形式化定义 → 为什么这样设计（对比直觉或朴素替代方案）”**的顺序。
- **避免两类常见陷阱**：
  - **防公式堆砌**：不连续抛出多行公式却缺乏物理意义与变量维度说明；复杂公式后紧跟直观解释（如各分项分别起激励或约束作用）。
  - **防代码直译**：用数学变换与模块功能描述算法，不把代码变量名（如 `feat_tmp`、`reshape` 操作细节）原样写成正文叙述。

## 方法与实验呼应

- **证明责任分离**：每个核心组件都要有设计理由；声称某组件有效或不可替代时，须有对应的消融实验（Ablation Study）或机制分析支持。**整体主实验（Main Results）证明完整系统有效，消融实验证明内部模块贡献**，不得把整体性能提升直接归因于单一子模块。
- **结果段四步结构**：按**“要检验的问题/假设 → 图表中的核心观察（指明具体表/图与比较条件） → 受证据支持的机制解释 → 适用边界或代价”**组织段落。保留实际的比较条件、指标方向（$\uparrow / \downarrow$）和统计范围；缺少对照或多次运行统计时主动降低结论强度，不从单次微弱优势推出普遍规律。

## 讨论、局限性与结论

- **讨论与局限性（Limitations）**：将客观实验观察与作者的推测解释明确区分。撰写 Limitations 时，聚焦于**方法假设边界**（如对特定分布或先验的依赖）、**计算/数据规模约束**或**实验中观察到的具体失败模式**，给出具体、可理解的边界说明，避免空洞套话或贬损已验证的核心贡献。
- **结论（Conclusion）**：用凝练语言回顾研究问题、核心方案与已证实的主要发现；未来工作与已完成贡献明确分开。

## 教学示例（自拟）

- **无依据泛化表述**：“Our module universally improves model robustness.”
- **有证据边界表述**：“On the evaluated corrupted-input benchmark, adding the module improves average accuracy over the tested baseline.”
- **使用边界**：后一句仍须真实实验数据支持；若尚未完成该实验，只能写为待验证的研究计划。
